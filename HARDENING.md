# Security Hardening & Remediation Log

This document catalogs every security vulnerability identified, remediated, and verified in the **HostelGrievance** codebase. Every finding is mapped directly to empirical proof in [`TEST-EVIDENCE.md`](TEST-EVIDENCE.md).

---

## Hardening Findings Matrix

| Finding | Risk | Change | Verification | Residual Risk |
| :--- | :--- | :--- | :--- | :--- |
| **HG-AUTHZ-001**: Broken Object-Level Authorization on `GET /api/grievances/:id` | Any authenticated student could read any other student's private grievance, room details, and comments by incrementing or guessing the grievance ID (IDOR). | Added `assertCanViewGrievance()` check verifying that the requesting user is either the author or has role `warden`/`admin`. | Re-tested with two separate student accounts. Student A requesting Student B's grievance receives `403 Forbidden`. Student A requesting own grievance and Warden requesting any grievance returns `200 OK`. Backed by [`evidence/HG-AUTHZ-001-idor.txt`](evidence/HG-AUTHZ-001-idor.txt) and automated test suite. | None identified for this endpoint. |
| **HG-AUTHZ-002**: Unauthorized Grievance Status Tampering on `PATCH /api/grievances/:id` | Authenticated students could unilaterally change their grievance status to "Resolved" or "In Progress", subverting the warden review workflow. | Implemented role-based check in `PATCH /api/grievances/:id` ensuring only `warden` or `admin` accounts can modify ticket status. | Verified that a student attempting to PATCH status receives `403 Forbidden`, while a warden updating status succeeds with `200 OK`. Backed by [`evidence/HG-AUTHZ-002-status-patch.txt`](evidence/HG-AUTHZ-002-status-patch.txt) and automated test suite. | None identified. |
| **HG-AUTHZ-003**: Insecure Direct Object Reference (IDOR) on Attachment Retrieval (`GET /api/attachments/:id`) | An attacker could download private photographic evidence submitted by other students by supplying the attachment ID. | Bound attachment retrieval to parent grievance authorization (`assertCanViewGrievance()`), ensuring non-permitted users cannot download attachments. | Verified that Student B attempting to download Student A's attachment receives `403 Forbidden`, while the author receives `200 OK`. Backed by [`evidence/HG-AUTHZ-003-attachment-idor.txt`](evidence/HG-AUTHZ-003-attachment-idor.txt) and automated test suite. | None identified. |
| **HG-AUTH-001**: Weak Password Hashing & Sensitive Credential Exposure | Potential credential compromise if database storage leaked; default hardcoded passwords allowed unauthorized administrative access. | Upgraded password derivation to salted `scrypt` (`passwords.ts`), required `SEED_ADMIN_PASSWORD` via environment variables, and stripped password hashes from all user query responses. | Verified scrypt hash generation in DB and confirmed `GET /api/admin/users` returns user objects without `passwordHash` fields. Backed by [`evidence/HG-AUTH-001-password-hashing.txt`](evidence/HG-AUTH-001-password-hashing.txt) and `admin.test.ts`. | Strong initial secrets must be maintained by operators in production `.env`. |
| **HG-AUTH-002**: Replay of Revoked Sessions Following Logout / Password Change | Stolen JWT access tokens remained usable until natural expiration even after the user logged out or changed credentials. | Integrated `TokenBlacklist` database table for explicit logout invalidation and incremented `User.tokenVersion` on password change to immediately kill all active sessions across devices. | Verified that replaying a token after `POST /api/logout` or password change returns `401 Unauthorized` ("Token has been revoked/logged out"). Backed by [`evidence/HG-AUTH-002-session-revocation.txt`](evidence/HG-AUTH-002-session-revocation.txt) and automated test suite. | Tokens remain valid for up to 15 minutes if network disruption prevents blacklist DB lookup. |
| **HG-AUTH-003**: Token Theft Replay via Network Hijacking | An attacker intercepting an access token on an insecure network could impersonate the victim from a foreign computer. | Embedded cryptographic client fingerprint (`SHA-256(IP + User-Agent)`) in the JWT payload (`fpt` claim) and enforced mismatch validation on every authenticated request. | Verified that replaying an intercepted token from a different client IP/User-Agent yields `401 Unauthorized` ("Session binding violation"). Backed by [`evidence/HG-AUTH-003-session-binding.txt`](evidence/HG-AUTH-003-session-binding.txt). | Users behind dynamic mobile CGNAT proxies changing IPs during a session must re-authenticate. |
| **HG-CSRF-001**: Cross-Site Request Forgery on State-Changing API Endpoints | Malicious third-party sites could execute forged state-changing mutations (e.g. creating grievances, comments, or warden accounts) via ambient browser cookies. | Added double-submit CSRF protection middleware in `app.ts` requiring valid `X-CSRF-Token` headers for all cookie-authenticated `POST`, `PUT`, `PATCH`, and `DELETE` requests. | Verified that requests with cookies omitting `X-CSRF-Token` fail with `403 Forbidden`, while requests with matching tokens succeed. Backed by [`evidence/HG-CSRF-001-csrf-validation.txt`](evidence/HG-CSRF-001-csrf-validation.txt) and automated test suite. | Bearer token-authenticated clients (mobile/CLI) bypass CSRF checking as intended. |
| **HG-INPUT-001**: Unrestricted File Upload & MIME Spoofing (Polyglot Attacks) | Attackers could upload malicious scripts disguised as images (e.g. SVG/HTML/PHP with `.png` extension) leading to Stored XSS or server compromise. | Replaced filename/header MIME checks with magic-byte file inspection (`detectMimeFromBytes()`) for JPEG, PNG, GIF, WebP, and enforced a 2 MB size ceiling. | Verified that uploading text or non-image files with image extensions returns `400 Bad Request`, while valid images succeed. Backed by [`evidence/HG-INPUT-001-magic-bytes.txt`](evidence/HG-INPUT-001-magic-bytes.txt) and automated test suite. | None identified for supported image types. |
| **HG-INPUT-002**: Rogue User Registration via Non-Institutional Emails | External attackers could register arbitrary accounts or spoof staff identities using public email providers. | Enforced strict `@giet.edu` domain regex validation on `signup`, `login`, and admin warden provisioning routes. | Verified that non-institutional emails (e.g. `hacker@external.com`) are rejected with `400 Bad Request`. Backed by [`evidence/HG-INPUT-002-domain-validation.txt`](evidence/HG-INPUT-002-domain-validation.txt) and automated test suite. | None identified. |
| **HG-DOS-001**: Brute-Force Authentication Flooding & Layer-7 Denial of Service | Unrestricted request volume allowed credential stuffing attacks and API resource exhaustion. | Implemented distributed token-bucket rate limiting (Redis with Lua script + in-memory fallback) and Nginx proxy zones (`10r/s` API, `30r/s` site). | Verified that rapid bursts of >5 authentication requests yield `429 Too Many Requests`. Backed by [`evidence/HG-DOS-001-rate-limiting.txt`](evidence/HG-DOS-001-rate-limiting.txt) and `rate_limit_test.py`. | In-memory fallback is per-process if Redis is disconnected. |
| **HG-CONF-001**: Hardcoded Localhost CORS & Missing Liveness Probing | Production deployments across custom domains failed CORS preflights, and orchestrators lacked liveness health probing. | Made CORS origins dynamic via `ALLOWED_ORIGINS` environment configuration and added `/api/health` checking active PostgreSQL connectivity. | Verified that `/api/health` returns `200 OK` (`database: connected`) and unauthorized CORS origins receive no `Access-Control-Allow-Origin` header. Backed by [`evidence/HG-CONF-001-cors-health.txt`](evidence/HG-CONF-001-cors-health.txt). | Operators must configure `ALLOWED_ORIGINS` accurately for production domains. |
| **HG-CONF-002**: Uncontainerized Rate Limiting & Monolithic Compose Stack | Multi-container deployments lacked central Redis state synchronization. | Updated `docker-compose.yml` to include a standalone `redis:7-alpine` service with healthcheck dependencies. | Verified clean Docker compose specification and service health dependencies. Backed by `docker-compose.yml`. | Single-node Redis container requires standard volume persistence for persistent quota tracking. |
